6. Requisitos Não Funcionais

Requisitos Não Funcionais - VibeU
RNF01 - Arquitetura Cliente-Servidor

Descrição: O sistema deverá seguir uma arquitetura cliente-servidor, mantendo separação entre frontend, backend e banco de dados.

Categoria: Arquitetura

RNF02 - API REST

Descrição: O backend deverá disponibilizar todas as funcionalidades através de uma API REST.

Categoria: Arquitetura

RNF03 - Banco de Dados Relacional

Descrição: Todos os dados da aplicação deverão ser armazenados em um banco de dados PostgreSQL.

Categoria: Banco de Dados

RNF04 - Autenticação JWT

Descrição: O sistema deverá utilizar autenticação baseada em JSON Web Token (JWT).

Categoria: Segurança

RNF05 - Controle de Acesso

Descrição: O sistema deverá implementar controle de acesso baseado em perfis:

Administrador
Organizador
Participante

Categoria: Segurança

RNF06 - Responsividade

Descrição: A interface deverá funcionar adequadamente em dispositivos desktop, tablet e smartphone.

Categoria: Usabilidade

RNF07 - Dockerização

Descrição: Toda a aplicação deverá ser executada em containers Docker.

Categoria: Infraestrutura

RNF08 - Docker Compose

Descrição: Os containers da aplicação deverão ser inicializados e gerenciados através do Docker Compose.

Categoria: Infraestrutura

RNF09 - Tratamento de Erros

Descrição: A API deverá retornar mensagens padronizadas para erros, exceções e validações.

Categoria: Qualidade de Software

RNF10 - Validação de Dados

Descrição: Todos os dados recebidos pela API deverão passar por validações antes de serem processados.

Categoria: Qualidade de Software

RNF11 - Segurança de Senhas

Descrição: As senhas dos usuários deverão ser armazenadas utilizando criptografia segura.

Categoria: Segurança

RNF12 - Versionamento da API

Descrição: A API deverá utilizar versionamento seguindo o padrão:

/api/v1

Categoria: Arquitetura

RNF13 - Escalabilidade

Descrição: A arquitetura deverá permitir futura evolução para microsserviços sem necessidade de reestruturação completa.

Categoria: Arquitetura

RNF14 - Versionamento de Código

Descrição: Todo o código-fonte deverá ser versionado utilizando Git e hospedado em repositório GitHub.

Categoria: DevOps

RNF15 - Integração Contínua

Descrição: O projeto deverá possuir pipeline de Integração Contínua utilizando GitHub Actions.

Categoria: DevOps

RNF16 - Manutenibilidade

Descrição: O código deverá seguir padrões de desenvolvimento definidos pela equipe, facilitando manutenção e evolução.

Categoria: Qualidade de Software

RNF17 - Logs da Aplicação

Descrição: O sistema deverá registrar logs para monitoramento, auditoria e depuração de erros.

Categoria: Observabilidade

RNF18 - Disponibilidade

Descrição: A aplicação deverá permanecer disponível durante demonstrações, apresentações acadêmicas e testes do projeto.

Categoria: Confiabilidade

RNF19 - Padronização de Respostas

Descrição: A API deverá possuir um padrão único para respostas de sucesso e erro.

Exemplo de Sucesso
{
  "success": true,
  "message": "Operação realizada com sucesso",
  "data": {}
}
Exemplo de Erro
{
  "success": false,
  "message": "Erro ao processar solicitação",
  "errors": []
}

Categoria: Arquitetura

RNF20 - Compatibilidade de Navegadores

Descrição: O frontend deverá funcionar corretamente nos principais navegadores modernos.

Exemplos:

Google Chrome
Microsoft Edge
Mozilla Firefox
Safari

Categoria: Compatibilidade

8. Regras de Negócio

RN01 - Cadastro Único de Usuário
Não deve existir mais de um usuário com o mesmo e-mail cadastrado no sistema.
RN02 - Senha Segura
A senha do usuário deverá possuir no mínimo:
    • 8 caracteres
    • 1 letra maiúscula
    • 1 letra minúscula
    • 1 número
RN03 - Login Apenas para Usuários Ativos
Somente usuários ativos poderão realizar autenticação.
RN04 - Apenas Organizadores Criam Eventos
Somente usuários com perfil ORGANIZER poderão criar eventos.
RN05 - Evento Deve Possuir Informações Obrigatórias
Todo evento deverá possuir:
    • Nome
    • Descrição
    • Data
    • Horário
    • Local
    • Capacidade máxima
    • Valor do ingresso
RN06 - Evento Deve Possuir Data Futura
Não será permitido cadastrar eventos em datas passadas.
RN07 - Evento Publicado Torna-se Visível
Apenas eventos publicados poderão ser visualizados pelos participantes.
RN08 - Evento Encerrado Não Aceita Inscrições
Eventos encerrados não poderão receber novas inscrições.
RN09 - Evento Cancelado Não Aceita Operações
Eventos cancelados não poderão receber:
    • Novas inscrições
    • Pagamentos
    • Check-ins
RN10 - Limite de Participantes
O número de participantes não poderá ultrapassar a capacidade máxima definida para o evento.
RN11 - Inscrição Única por Evento
Um participante poderá realizar apenas uma inscrição por evento.
RN12 - Participante Deve Estar Autenticado
Somente usuários autenticados poderão realizar inscrições.
RN13 - Pagamento Vinculado à Inscrição
Todo pagamento deverá estar associado a uma inscrição válida.
RN14 - Pagamento Deve Ser Confirmado
Somente pagamentos aprovados poderão gerar ingressos.
RN15 - Um Ingresso por Inscrição
Cada inscrição poderá gerar apenas um ingresso.
RN16 - Código de Ingresso Único
Todo ingresso deverá possuir um código único.
Exemplo:
VBU-2026-000001
RN17 - QR Code Exclusivo
Cada ingresso deverá possuir um QR Code único.
RN18 - Check-in Apenas com Ingresso Válido
O check-in somente poderá ser realizado mediante apresentação de ingresso válido.
RN19 - Check-in Único
Um ingresso poderá realizar apenas um check-in.
RN20 - Registro da Entrada
Ao realizar check-in o sistema deverá registrar:
    • Data
    • Hora
RN21 - Exclusão de Evento
Somente eventos sem participantes poderão ser excluídos.
RN22 - Atualização de Vagas
Sempre que ocorrer:
    • Inscrição
    • Cancelamento
o sistema deverá recalcular automaticamente as vagas disponíveis.
RN23 - Controle de Permissões
Administradores possuem acesso total ao sistema.
RN24 - Controle de Acesso por Perfil
Cada funcionalidade deverá respeitar o perfil do usuário:
    • ADMIN
    • ORGANIZER
    • PARTICIPANT
RN25 - Histórico de Participação
O sistema deverá manter o histórico de eventos dos participantes.
RN26 - Auditoria
Todas as entidades deverão armazenar:
    • createdAt
    • updatedAt
RN27 - Evento Possui Um ou Mais Lotes
Todo evento poderá possuir um ou mais lotes.
RN28 - Inscrição Deve Estar Associada a um Lote
Toda inscrição deverá estar vinculada a um lote.
RN29 - Controle de Quantidade por Lote
Cada lote deverá possuir uma quantidade máxima de ingressos.
RN30 - Lote Esgotado
Quando atingir o limite de ingressos, o lote será marcado como esgotado.
RN31 - Valor do Pagamento
O valor da inscrição será definido pelo lote escolhido.
